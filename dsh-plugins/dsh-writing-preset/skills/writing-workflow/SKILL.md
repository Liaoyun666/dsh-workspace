# 长文写作流程

写作质量主要来自流程，而不是一次成型的灵感。按阶段推进，每一步都留下可检查的产物。

## 1. 澄清需求（Brief）

最少确认六项。用户没说、也无法从上下文推断时，用 `ask_user_question` 一次问清（不要逐条追问）：

| 维度 | 要问清的问题 |
|---|---|
| 读者 | 谁读？他们已知什么、关心什么、会拿它做什么决定？ |
| 目的 | 这篇文字要改变读者的认知、情绪还是行动？ |
| 体裁 | 报告 / 提案 / 评论 / 教程 / 新闻稿 / 演讲稿 / 书稿章节？ |
| 篇幅 | 目标字数或页数；信息密度比长度重要。 |
| 语气 | 正式 / 中立 / 亲切 / 犀利；第一人称还是第三人称？ |
| 交付 | Markdown、Word、PPT、Excel？落在哪个文件？截止时间？ |

把确认结果压缩成 3–5 行，写在回复最前面或工作区的 `brief.md` 里，作为后续取舍的依据。用户要求直接出稿时，跳过提问，但要把假设写出来。

## 2. 调研与事实卡

- 只调研与核心论点直接相关的事实。先列 5–10 个必须回答的问题，再检索。
- 每个会被引用的关键事实建一张「事实卡」：结论、来源、发布时间、原文关键句、可信度（高 / 中 / 低）。
- 至少两个独立来源互相印证；只有单一来源的，写作时明确标注不确定性。
- 查不到的事实不写进正文；必须写时标注「待核实」。检索与引用方法见 `research-and-citation` 技能。

## 3. 先纲后稿

- 用 `todo_write` 把任务拆成：提纲 / 各节初稿 / 统稿 / 校对 / 交付。
- 提纲写到二级标题，每个标题下用一句话写清「这一节要证明什么」，并标出哪里需要数据。
- 超过 3000 字，先把提纲给用户过目；确认后再展开。短文可省略确认，但回复中仍要说明结构。
- 检查提纲：论点是否递进、是否有重复、每节是否服务目的；删掉哪一节读者仍能读懂，就删掉。

## 4. 分节起草

- 一节一次写透：先写主题句，再补证据与例子，最后检查与前后文的衔接。
- 全篇保持统一的人称、时态、术语与格式；术语表可维护在 `glossary.md`。
- 初稿允许粗糙，但事实、数字、引语必须当场核对，不能留到「后面再说」。
- 长文写入工作区文件（如 `draft.md`），每完成一节就落盘，避免上下文丢失。

## 5. 修改（至少两遍）

第一遍看结构：

- 开篇是否在第一段内交代「为什么值得读」？结尾是否收束到目的？
- 每节是否有一个中心句？段与段之间是否有逻辑连接而不是并列堆叠？
- 有没有可以整段删掉而不损失信息的段落？
- 论据是否支撑论点，还是只是相关？

第二遍看句子：逐段执行 `chinese-editing` 技能里的检查清单。

## 6. 交付检查

- 标题、副标题、署名、日期、版本号齐全且一致；
- 目录与编号连续（如适用）；
- 引用与参考列表完整，正文编号与列表一一对应；
- 文件命名 `主题-版本-日期`，保存在工作区，不覆盖用户原稿；
- 用 `present` 交付，并说明文件路径、字数、结构概览，以及仍需用户确认的问题。

## 常见失败模式

- 提纲没定就开写，写到一半发现论点不成立；
- 用形容词代替证据（「效果显著」「广受好评」）却不给数据或出处；
- 每节都从零介绍背景，读者被迫重复阅读；
- 为了凑字数加套话，或为了显得高级堆术语。
